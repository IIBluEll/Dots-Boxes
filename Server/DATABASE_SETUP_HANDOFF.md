# Dots & Boxes 계정 DB 구축 작업 지시서

## 요청

이 서버 컴퓨터에 Dots & Boxes의 PostgreSQL 계정 저장 기반을 구축해 주세요. 아래 범위의 설치·설정·코드 작성·마이그레이션·테스트를 수행하고, 실제 적용 결과와 클라이언트 담당자에게 넘길 정보를 정리해 주세요. 계획만 제시하지 말고 가능한 범위의 작업을 완료해 주세요.

기존 서비스나 데이터 삭제, 기존 DB 초기화, 외부 포트 공개, 운영 서버 중단이 필요하면 해당 작업 직전에 이유와 정확한 대상을 설명하고 승인을 받으세요. 관련 없는 서비스와 사용자 변경 사항은 보존하세요.

## 프로젝트와 현재 진행 상태

- 게임: Unity 기반 Dots & Boxes. 첫 출시 범위는 일반 온라인 대전과 로컬 2인입니다.
- 랭크, AI, 상점, 재화, 전적 저장은 이번 범위가 아닙니다.
- 사용자 확인 완료: Android 실기기에서 Google Play Games 로그인, 게임 UI의 닉네임 표시, 서버 인증 코드 발급 성공.
- Google 인증 코드의 서버 검증과 게임용 로그인 토큰 발급은 아직 후속 작업입니다.
- 기준 저장소의 서버 프로젝트: `Server/DotsAndBoxes.Server/DotsAndBoxes.Server.csproj`.
- 지시서 작성 시 해당 프로젝트는 `net9.0`, Nullable 및 TreatWarningsAsErrors 활성화 상태였고, 계정 DB 라이브러리 참조가 없었습니다. 서버 컴퓨터의 체크아웃은 다를 수 있으니 직접 확인하세요.
- 기존 경기의 `UserId`는 C# `Guid`입니다. 이 타입과 Shared 게임 규칙은 유지하세요.
- 로컬 PC의 저장소 경로를 이 컴퓨터의 경로로 가정하지 마세요.
- 로그인 수단은 Google Play Games입니다. 별도 아이디·비밀번호 회원가입은 만들지 않습니다.

## 1. 작업 전 환경 확인

1. 적용되는 AGENTS.md와 저장소 지침을 읽으세요.
2. 작업 디렉터리, Git 브랜치와 변경 상태, 서버 프로젝트 위치를 확인하세요. 저장소가 없으면 위치/저장소 정보를 사용자에게 물어보세요. 임의의 저장소를 새로 만들지 마세요.
3. OS, .NET SDK, PostgreSQL 설치 여부·버전·실행 상태, 컨테이너 사용 여부, 사용 중인 포트를 확인하세요.
4. 기존 DB/역할/볼륨이 있다면 이름과 용도를 확인하고 재사용 가능성을 판단하세요. 비밀번호나 연결 문자열 원문을 출력하지 마세요.
5. 사용 중인 PostgreSQL 배포 방식을 우선 존중하세요. 새 설치가 필요하면 OS와 운영 방식에 적합한 유지보수 중인 버전을 공식 문서로 확인하고 선택 이유를 짧게 남기세요. 설치 방식이 시스템에 큰 영향을 준다면 구체적인 방식을 제시하고 확인받으세요.
6. EF Core 및 Npgsql을 사용한다면 실제 프로젝트의 대상 프레임워크와 호환되는 버전을 선택하세요. 임의로 .NET 전체 프로젝트를 업그레이드하지 마세요. 지원 종료 문제를 발견하면 별도로 보고하세요.

## 2. PostgreSQL 실행 및 접근 설정

- 전용 DB 예시: `dotsandboxes`. 이름이 충돌하면 기존 DB를 덮어쓰지 말고 전용 이름을 정하세요.
- 앱 런타임 접속용 전용 역할을 만드세요. superuser나 DB 생성 권한을 주지 마세요.
- 스키마 변경용 마이그레이션 역할과 런타임 역할을 분리하세요. 런타임에는 필요한 테이블 DML과 실제로 필요한 시퀀스 권한만 부여하세요.
- 서버 프로세스와 DB가 같은 호스트라면 로컬 연결을 우선하세요. 컨테이너라면 필요한 내부 네트워크만 사용하세요.
- Unity는 DB에 직접 연결하지 않습니다. 클라이언트 PC에서 접속시키기 위해 DB 5432 포트를 인터넷에 공개하지 마세요.
- 비밀번호는 충분히 무작위로 생성하고 서버의 비밀 설정에 보관하세요. 저장소·문서·테스트 코드·채팅에 실제 비밀번호를 넣지 마세요.
- 개발 환경은 .NET User Secrets, 배포 환경은 기존 비밀 관리 방식 또는 접근 제한된 환경 설정을 사용하세요. 실제 서비스 계정이 해당 설정을 읽을 수 있는지 확인하세요.
- PostgreSQL이 재시작되어도 데이터가 유지되도록 디스크/볼륨 경로를 확인하세요. 재시작 테스트는 새 전용 인스턴스에서만 수행하고, 공유 인스턴스라면 기존 서비스에 영향 없는 검증으로 대체하세요.

## 3. 최소 계정 스키마

아래는 논리 이름입니다. 물리 테이블/컬럼은 PostgreSQL 소문자 snake_case를 사용하고, C# 모델과 명시적으로 매핑하는 방식을 권장합니다. 저장소에 기존 규칙이 있으면 일관성을 우선하세요.

### Users / users

| 논리 필드 | PostgreSQL 타입 | 제약 및 의미 |
|---|---|---|
| UserId | uuid | 기본키. 서버가 생성. Guid.Empty 값 금지 |
| DisplayName | text | NOT NULL. 표시용 닉네임. 공백만 있는 값 금지 |
| CreatedAtUtc | timestamptz | NOT NULL. 최초 생성 시각 |
| UpdatedAtUtc | timestamptz | NOT NULL. 프로필 갱신 시각 |

- 닉네임은 고유키가 아닙니다. 같은 닉네임을 가진 서로 다른 계정을 허용하세요.
- 닉네임에는 한글·이모지 등 Unicode 문자열을 저장할 수 있어야 합니다.
- 게임 규칙의 승패·점수·현재 경기 상태를 이 테이블에 추가하지 마세요.

### ExternalIdentities / external_identities

| 논리 필드 | PostgreSQL 타입 | 제약 및 의미 |
|---|---|---|
| Provider | text | NOT NULL. 이번 제공자는 `GOOGLE_PLAY_GAMES` |
| ProviderApplicationId | text | NOT NULL. 서버에 설정된 PGS 게임 프로젝트 ID |
| ProviderPlayerId | text | NOT NULL. Google 서버 검증으로 얻은 Player ID |
| UserId | uuid | NOT NULL. users.user_id 외래키 |
| CreatedAtUtc | timestamptz | NOT NULL. 연결 생성 시각 |

- `(Provider, ProviderApplicationId, ProviderPlayerId)`에 복합 기본키 또는 UNIQUE 제약을 두세요. 기본키와 같은 컬럼의 중복 UNIQUE 인덱스는 만들지 마세요.
- Provider 계열 문자열은 빈 문자열/공백만 있는 값을 거부하세요. Player ID는 불투명 문자열로 취급하고 소문자 변환이나 숫자 변환을 하지 마세요.
- `ProviderApplicationId`는 Android 패키지명이나 Web Client ID가 아닙니다.
- UserId 외래키에 역조회용 인덱스를 두세요. 계정 삭제 정책이 정해지지 않았으므로 이번에는 임의의 연쇄 삭제보다 RESTRICT/NO ACTION을 사용하세요.
- 명시적인 계정 연결 요청 없이 외부 식별자를 다른 UserId로 옮기거나 닉네임/이메일로 계정을 합치지 마세요.
- Google 인증 코드, Access Token, Client Secret, 게임 JWT는 이 두 테이블에 저장하지 마세요.

## 4. ASP.NET 서버 저장 계층과 마이그레이션

가능하면 기존 ASP.NET 서버 프로젝트에 EF Core + Npgsql로 구성하세요. 이미 다른 저장 계층이 존재하면 중복 프레임워크를 도입하기 전에 현재 구조를 확인하세요.

필요한 산출물:

1. Users / ExternalIdentities 엔터티와 모델 매핑.
2. DbContext 및 연결 설정 등록. 권장 설정 키: `ConnectionStrings:GameDatabase`.
3. 초기 계정 스키마 마이그레이션과 검토 가능한 적용 SQL.
4. 검증 완료된 외부 계정을 받아 계정을 조회하거나 생성하는 서비스.
5. 실제 PostgreSQL을 사용하는 통합 테스트.

계정 서비스의 논리 계약은 다음과 같습니다. 이름은 기존 컨벤션에 맞게 조정해도 됩니다.

```text
GetOrCreateExternalUser_async(
    provider,
    providerApplicationId,
    providerPlayerId,
    verifiedDisplayName,
    cancellationToken)
    -> UserId, DisplayName
```

계약의 신뢰 경계:

- 이 서비스 입력은 후속 Google 서버 검증을 통과한 값이어야 합니다.
- 이번에 임의의 Player ID/닉네임을 받아 로그인 처리하는 공개 HTTP API를 만들지 마세요.
- ProviderApplicationId는 후속 인증 서비스의 서버 설정에서 전달해야 합니다.
- Google 검증/API, JWT 발급, SignalR 인증 교체는 이번 작업에 포함하지 않습니다.

필수 동작:

- 외부 계정 연결이 있으면 기존 UserId를 반환하고 표시 이름을 갱신합니다.
- 연결이 없으면 Users와 ExternalIdentities를 하나의 트랜잭션으로 생성합니다.
- 동일 계정에 대한 동시 요청은 DB 고유 제약을 이용해 안전하게 처리하고 모두 같은 UserId로 수렴해야 합니다.
- 단순한 '조회 후 없으면 INSERT'만으로 동시성 처리를 끝내지 마세요. 고유키 충돌 시 실패한 트랜잭션을 올바르게 롤백하고 기존 계정을 재조회하세요.
- 충돌/취소/실패 시 외부 연결 없는 Users 레코드가 남지 않아야 합니다.
- 기존 계정의 CreatedAtUtc는 갱신하지 않습니다.
- 닉네임이 비어 있거나 프로필 조회가 실패한 경우의 정책을 문서화하세요. 기존 닉네임을 공백으로 덮어쓰지 마세요.

마이그레이션은 명시적인 관리 단계로 적용하세요. 운영 앱이 시작될 때마다 스키마 생성·초기화·삭제를 자동 수행하게 만들지 마세요. `EnsureDeleted` 또는 기존 DB 드롭으로 오류를 해결하지 마세요.

새 코드는 사용자 컨벤션을 따르세요: private/protected 멤버 `_camelCase`, static 필드 `s_camelCase`, const/readonly 필드 `UPPER_SNAKE_CASE`, 함수 PascalCase, 실제 비동기 함수 `_async` 접미사, enum 이름/요소 `UPPER_SNAKE_CASE`. 기존 코드를 무관하게 일괄 변경하지 마세요.

## 5. 필수 검증

테스트는 별도의 테스트 DB/스키마에서 수행하세요. 운영 데이터와 같은 이름을 사용하지 마세요.

1. 새 DB에 초기 마이그레이션 적용 성공, 같은 마이그레이션을 다시 적용해도 오류 없음.
2. 외부 계정 최초 등록 시 Users 1개와 ExternalIdentities 1개 생성.
3. 같은 외부 계정 재조회 시 동일한 UserId 반환, 레코드 수 증가 없음.
4. 같은 외부 계정 동시 요청 시 동일 UserId 반환, 중복/고아 계정 없음.
5. 같은 닉네임을 가진 서로 다른 Player ID가 서로 다른 UserId를 받음.
6. 기존 외부 계정의 닉네임 변경 시 UserId와 CreatedAtUtc 유지.
7. 외래키 위반, 빈 식별값, Guid.Empty 등 잘못된 데이터 거부.
8. 실패 시 트랜잭션 원자성 유지. 최소한 UNIQUE 충돌 상황의 롤백/재조회 확인.
9. 실제 런타임 역할로 계정 조회·생성 가능, 스키마 변경 권한은 없음.
10. 앱 프로세스를 다시 실행해도 같은 계정과 UserId를 조회 가능.
11. 서버 빌드와 영향받는 기존 서버 테스트 통과.

DB 통합 테스트 통과와 Google 실계정 인증 성공은 다른 검증입니다. Google 인증은 이번 범위에서 검증하지 않았다고 정확히 보고하세요.

## 6. 운영 및 인계 문서

`Server/DATABASE_SETUP.md` 등 저장소 문서에 다음을 남기세요.

- 실제 OS, PostgreSQL 버전, 설치 방식, 서비스/컨테이너 이름.
- DB 이름, 접속 방식, 데이터 영속 저장 위치. 비밀값 제외.
- 런타임/마이그레이션 역할 및 권한 구분.
- 사용한 NuGet 패키지와 버전, 실제 마이그레이션 이름.
- 마이그레이션 적용/확인 명령. 비밀번호는 플레이스홀더 사용.
- 비밀값이 저장된 설정 이름과 주입 방법. 값 자체는 기록하지 않음.
- 안전한 백업·복원 절차. 전용 테스트 DB에서 복원 검증이 가능하면 수행하고 결과 기록.
- 모든 필수 테스트 결과와 미검증 항목.
- 기존 서버 실행 방식에 변경이 있는지와 새 필수 설정 때문에 기존 테스트가 영향을 받는지.

최종 답변에는 클라이언트 담당 Codex에게 전달할 다음 정보를 포함하세요.

1. 작업 브랜치와 변경 파일 목록. 커밋은 사용자가 요청한 경우에만 수행하고 커밋했다면 해시 포함.
2. 계정 서비스의 실제 네임스페이스, 함수 시그니처, 반환 타입, DI 등록 방법.
3. 연결 문자열 설정 키와 다음 개발자가 해야 할 로컬 설정. 실제 비밀번호 제외.
4. 서버 인증 API 구현 시 연결해야 할 호출 지점.
5. 테스트 결과, 남은 작업, 재현 가능한 실행 명령.

## 이번 작업 완료 기준

실행 중인 PostgreSQL에 계정 스키마가 적용되고, ASP.NET 서버 저장 계층으로 동일 외부 계정이 항상 동일 UserId에 연결되며, 동시 요청과 재실행 검증이 통과한 상태입니다. Google 로그인 API, JWT, Unity, 매칭 닉네임 전달은 후속 작업으로 남겨 주세요.
